## 1. Проект и архитектура

Сайт «ЦЕНТР рекламно-выставочных услуг» (застройка выставочных стендов).

- **Стек:** Python 3.13, Flask 3.1.3, Werkzeug 3.1.9, Jinja, Pillow 12.3.0, pytest; обычные CSS/JS без
  сборщиков (без React/Tailwind/npm). Node v24 — только для тестов JS (`stand-plan.js`, галерея).
- **Приложение** (`app/`): фабрика `create_app` — `app/__init__.py` (настройки, CSP, фильтры картинок,
  команды `check-content`, `make-image-sizes`, `hash-password`); публичные маршруты — `app/routes.py`
  (`/`, `/<slug>`, `/media/<path>`); админка — `app/admin.py` (`/admin`); вход и CSRF — `app/auth.py`;
  загрузка и обработка фото — `app/uploads.py`; атомарная запись JSON, история, блокировка —
  `app/storage.py`; чтение и проверка контента, ссылки Vimeo — `app/content.py`; портфолио и карточки
  главной — `app/portfolio.py`; черновики редактора — `app/drafts.py`; поля редактора — `app/texts.py`.
- **Страница одна:** главная + разделы-«шторки» (`/portfolio`, `/about`, `/contacts` открывают ту же
  страницу с открытой шторкой). Портфолио целиком лежит в HTML главной.
- **Анимация сборки стенда:** 160 кадров `app/static/img/stand/frame-000…159.webp` (1280×720, ≈3,9 МБ),
  `FRAME_COUNT = 160` в `app/routes.py`, логика — `initScene()` в `app/static/js/main.js` (кадр зависит
  от прокрутки: первые 0,75 экрана — «разборка» 159 → 0, дальше «сборка» 0 → 159). Не менялась.
- **Конфигуратор стенда:** `app/templates/sections/configurator.html` + `app/static/js/stand-plan.js`.
- **CSP** (`app/__init__.py`): всё `'self'`, iframe — только `frame-src https://player.vimeo.com`.
- **Git:** проекта **нет в Git**. `.gitignore` подготовлен: исключены `.env*`, `backup/`, `.venv/`,
  `content/media/*` (кроме `content/media/home/README.txt`), `content/originals/`, `content/.history/`,
  `.drafts/`, `.cache/`, `.lock`, `*.tmp`, `.playwright-mcp/`, `.claude/settings.local.json`.
- **Рядом:** `~/Desktop/CLOUDE/CRVU-REDESIGN` — отдельная альтернативная версия (порт 5056), её не трогать.

  адресам (включая `../` и `%2e%2e`) отвечают 404 — проверено тестами и вручную.

## 2. Работа с портфолио (админка `/admin`)

Админка включается, только когда заданы `SECRET_KEY`, `ADMIN_USERNAME`, `ADMIN_PASSWORD_HASH`
(окружение или `.env` в корне; хеш — `flask --app app hash-password`). `.env` не открывать и не печатать.

- **Основной сценарий (с 16.10):** «Добавить проект» → название, год, несколько фото, «Опубликовать сразу»
  (включено по умолчанию) → «Сохранить проект»: проект и фото — одной формой (`new_project`, лимит 200 МБ),
  фото через общий `_store_photos`; без загруженных фото — черновик. Те же файлы (SHA-256 с оригиналами
  проекта и внутри пачки) второй раз не добавляются. ZIP-импорт — свёрнутый блок «Дополнительно».
- **Импорт папки (с 16.10):** «Проекты» → «Импортировать папку» (`/admin/projects/import-folder`,
  `<input webkitdirectory>`): `static/js/admin-import.js` оставляет только фото, даёт миниатюры, порядок,
  «Убрать» и обложку, название — из имени папки; отправка — в обычный `new_project` (по умолчанию черновик).
  Сервер сам пропускает не-фото (`uploads.skip_reason`, общая с ZIP). Только на этой странице CSP
  разрешает `img-src blob:` для миниатюр.
- **Форма проекта и порядок по дате (с 16.10):** в форме 7 полей — название, выставка, месяц, год, площадь
  (обязательные; `month` 1–12, `area` — число м²), описание, Vimeo. Старые поля (`city`, `category`,
  `specs`, `example`, `order`) не показываются и не стираются. Порядок — `portfolio.chronological_key`
  (год ↓, месяц ↓, название) и на сайте, и в админке; список админки — по месяцам (`month_groups`,
  `<details>`). Маршрут `/move` и кнопки ↑ ↓ удалены.
- **Фильтры портфолио (с 19.10):** классификация — `portfolio.py` (`LAYOUT_FILTER` — порядок и схемы
  планировок, `AREA_RANGES`/`area_range`, `project_floors`), карточки получают `data-layout/area/floors`;
  `static/js/portfolio-filter.js` только сравнивает, прячет, пересчитывает счётчики и пишет выбор в адрес.
  Новое необязательное поле проекта `floors` (1/2, `content.FLOORS`) + выбор «Этажность» в форме проекта;
  у 4 рабочих проектов его нет. Публичного поиска нет. Тесты — `tests/test_portfolio_filters.py`.
- **Конфигуратор без опций и второго этажа (с 16.10):** из `sections/configurator.html`, `main.js`,
  `stand-plan.js` (`deckRect`), `style.css` (`.plan-deck`, галочка у чипа-флажка) и редактора текстов
  (`texts.py`) убраны «Опции» и тип с `deck`. В `content/home.json` записи `options` и тип «Двухэтажный»
  (`deck: true`) остались (контент не трогали по просьбе) — шаблон пропускает типы с `deck`. Четыре типа —
  сеткой `.cfg-types` (2 × 2 / в ряд). Тесты — `tests/test_configurator.py`.
- **Планировка (с 16.10):** поле `layout` ∈ `content.LAYOUTS` (Угловой, Остров, Линейный, Полуостров),
  хранится словом как показывается. Обязательна при создании (форма, импорт папки, ZIP — ZIP теперь тоже
  требует выставку, месяц, площадь) и для публикации (`set_status`). Исключение: правка старого проекта,
  у которого `layout` ещё нет (`read_form(layout_required=False)`), ключ тогда не пишется. У всех 4
  рабочих проектов планировки нет. На сайте не выводится.
- **Выставки (с 16.10):** `app/exhibitions.py` — событие = нормализованное название + год (`event_key`),
  справочник = `content/exhibitions.json` (необязательный, заранее добавленные) + выставки из проектов.
  Проект по-прежнему хранит `exhibition` (название) — миграции не было. Форма: `<datalist>` подсказок,
  `resolve` при сохранении берёт написание существующего события того же года. `/admin/exhibitions` —
  список по годам, добавление, удаление пустой. `/admin` — дерево год → месяц → выставка, поиск `q` и
  фильтры `year`, `month`, `event`, `layout` (GET, без JS; все — через `exhibitions.matches`, значения
  планировки — `content.LAYOUTS`; пригодно и для будущего фильтра на сайте). У Интермы и Transfaire месяца нет.
- **Проекты:** создание (`/admin/projects/new`), редактирование полей, публикация и снятие с публикации, удаление. Опубликовать без фото нельзя; удалить
  последнее фото опубликованного проекта нельзя (сначала снять с публикации).
- **Импорт стенда из ZIP:** «Проекты» → «Импорт стенда из ZIP» (`POST /admin/projects/import`, ZIP
  выбирают вручную): одна папка фото → черновик (название — поле, имя папки или архива; порядок — по
  именам, первое фото — обложка). Фото идут через ту же функцию `_store_photos`, что и обычная загрузка;
  архив не распаковывается на диск (`uploads.read_zip`/`read_zip_photo`); пределы те же (200 МБ, 20 фото,
  40 МБ), плюс `ADMIN_ZIP_MAX_RATIO = 10`; отказ при `..`/абсолютных путях, ссылках, шифровании,
  вложенных или нескольких папках. Подборки хранить в `project_photos/<стенд>/` (вне Git, не
  раздаётся сайтом, архив — `scripts/backup-project-photos.sh`); импорт их не меняет и не сканирует.
- **Фото:** загрузка пачкой (лимиты — раздел 3), обложка (первое фото), порядок вверх/вниз, удаление.
  Удаление фото переносит основной файл, версии и оригинал в `.history/` под одной меткой времени;
  удаление проекта — его папки `media/portfolio/<id>/` и `originals/portfolio/<id>/`.
- **Главная, блок «Реализованные проекты»:** Редактор (`/admin/editor`) → группа «Проекты» →
  «Выбрать проекты…» (до 6, хранятся только id в `home.json`) → «Сохранить черновик» → «Опубликовать».
  Удалённый из портфолио проект помечается «Удалён из портфолио» и убирается кнопкой «Убрать».
  Без выбранных проектов блок на главной не показывается.
- **Черновик и публикация:** редактор (`site.json`, `home.json`) сохраняет правки в `content/.drafts/`,
  на сайт они попадают только по «Опубликовать»; «Отменить черновик» возвращает опубликованное.
  Страница «Тексты» (`/admin/texts`) сохраняет сразу.
- **Восстановление версий:** «История версий» редактора восстанавливает выбранную копию `site.json` или
  `home.json` в черновик (дальше — проверить предпросмотр и опубликовать). Проекты и фото кнопкой не
  восстанавливаются: вручную — перенести файлы из `.history/media|originals/<время>/…` обратно с той же
  структурой и вернуть запись проекта из копии `portfolio.json`.
- **Видео Vimeo:** поле «Ссылка на видео» (`video` в `portfolio.json`) принимает только Vimeo:
  `vimeo.com/<id>`, закрытое `vimeo.com/<id>/<hash>`, ссылки каналов, групп, подборок,
  `player.vimeo.com/video/<id>?h=<hash>`. Из ссылки берутся только номер и hash
  (`content.vimeo_player_url`), адрес плеера — `https://player.vimeo.com/video/<id>?h=<hash>&dnt=1`.
  В галерее стенда кнопка «Смотреть видео»: iframe создаётся **только по нажатию** (до этого к Vimeo нет
  ни одного запроса), без автозапуска (`allow="encrypted-media; picture-in-picture"`, `allowfullscreen`,
  `referrerpolicy="strict-origin-when-cross-origin"`, `loading="lazy"`), встаёт на место фото; удаляется
  при «К фото», стрелках, миниатюрах, клавишах ←/→, закрытии окна и переходе к другому стенду. Не
  загрузился за 10 с — сообщение и возврат к фото. Под карточкой портфолио — ссылка на страницу Vimeo.

## 3. Обработка изображений (значения из `app/__init__.py` и `app/uploads.py`)

| Предел | Значение |
|---|---|
| Один файл (`ADMIN_MAX_IMAGE_BYTES`) | 40 МБ (проверка до обработки) |
| Один запрос загрузки (`ADMIN_MAX_UPLOAD_BYTES`) | 200 МБ — 4 фото по 40 МБ (5 — если каждое чуть меньше: multipart добавляет служебные данные); превышение — сообщение в админке, не 500 |
| Файлов за раз (`ADMIN_MAX_FILES`) | 20 |
| Разрешение (`ADMIN_MAX_PIXELS`) | 100 Мп; PNG и WebP — 50 Мп (`ADMIN_MAX_PIXELS_FULL_DECODE`: декодируются целиком). Проверка по заголовку, до декодирования; размер файла и пиксели — независимые пределы |
| Прочие запросы | публичная часть — 64 КБ, формы админки — 512 КБ |

- **Форматы:** JPG/JPEG, PNG, WebP — тип проверяется по содержимому (Pillow), не по имени. JPEG с блоком
  MPF (Pillow: «MPO», многие камеры и iPhone) принимается, если первый кадр — JPEG. **HEIC не
  поддерживается** (нужна зависимость `pillow-heif`, не согласована) — перед загрузкой конвертировать в JPEG.
- **Обработка:** поворот по EXIF, перевод в sRGB, прозрачность сохраняется; основной файл `NN.webp` до
  2560 px (качество 85), версии 640/1280/1920 по длинной стороне (качество 80/82/84), меньше исходника
  не увеличиваются. Метаданные (EXIF, GPS, XMP) в WebP не попадают. Большие JPEG декодируются сразу
  уменьшенными (`uploads.jpeg_reduction`: обычные кадры — как раньше, панорамы — с запасом 2 × 2560).
  Публичные файлы — права 0644.
- **Оригиналы:** сохраняются **до** обработки, байт в байт, в `content/originals/`, права 0600, без
  перезаписи (номер свободен и среди фото, и среди оригиналов). Сбой обработки, записи или прерывание
  пачки (таймаут воркера) → оригинал переносится в `.history/originals/`, фото пачки не остаются вне
  `portfolio.json`. Загрузки идут по одной под `content/.lock`.
- **srcset** (`media_srcset` в `app/__init__.py`): версии с **настоящей** шириной из заголовка файла
  (у вертикального снимка «640» — 427w) и основной файл, если он шире самой крупной версии. Не
  добавляются: нечитаемые файлы, основной файл с геометкой в EXIF, `static/`. Нет версий — `srcset`
  пуст. Карточки берут `-640` со `srcset`/`sizes` и `loading="lazy"`; галерея — `src` 1920 (или основной
  файл) и `srcset`; миниатюры ленты — 640. `flask --app app make-image-sizes` создаёт только
  недостающие версии старых фото.

## 4. История и резервное копирование

- **`HISTORY_KEEP = 500`** (`app/storage.py`): последние 500 копий **каждого** JSON. Удалённые фото и
  оригиналы в `.history/media|originals/` не удаляются. Папку `.history` вручную не чистить без плана.
- **`scripts/backup-content.sh`** — архив всего `content/` (JSON, `media/`, `originals/`, `.history/`,
  `.drafts/`) **без** `content/.cache/` и `content/.lock`; `.env` в архив не входит. Берёт ту же
  блокировку `content/.lock` (Python `fcntl`), что и админка; проверяет, что архив не пустой, читается и
  содержит `portfolio.json`; имя `crvu-content-ГГГГММДД-ЧЧММСС.tar.gz`, права 0600; старые архивы не
  удаляет и не перезаписывает; отказывается писать архив внутрь `content/`.
- **Куда:** `CRVU_BACKUP_DIR`, иначе `~/CRVU-backups` (создаётся). Контент — `CRVU_CONTENT_DIR` или `content/`.

```bash
scripts/backup-content.sh                                         # → ~/CRVU-backups
CRVU_BACKUP_DIR=/Volumes/<диск>/CRVU-backups scripts/backup-content.sh
# проверка восстановления — только во временную папку:
mkdir -p /tmp/crvu-restore && tar -xzf ~/CRVU-backups/crvu-content-<дата>.tar.gz -C /tmp/crvu-restore
CRVU_CONTENT_DIR=/tmp/crvu-restore/content CRVU_ENV_FILE= .venv/bin/flask --app app check-content
```

- **Внимание:** архив на том же компьютере (и папка `backup/`) не защищает от потери диска — храните
  архивы на внешнем диске или в облаке. **Автоматического расписания нет**: запускать вручную, после
  каждой сессии загрузки фото. Внешнее автоматическое копирование на сервере не настроено.
- **Первый архив (16.10.2026):** `scripts/backup-content.sh` → `~/CRVU-backups/crvu-content-20261016-170927.tar.gz`,
  408 КБ, права `-rw-------`, код завершения 0. Внутри: 5 JSON, `media/` — 1 файл (`home/README.txt`),
  `originals/` — 0 файлов, `.history/` — 52 файла, `.drafts/` — пустая папка; `.cache/` и `.lock` не попали.
  Архив восстановлен во временную папку scratchpad (не поверх рабочего `content/`): `check-content` —
  «Контент в порядке», содержимое совпало с рабочим `content/`. Рабочий контент не изменился, новый файл
  появился только в `~/CRVU-backups`. Архив лежит на этом же компьютере и от потери диска не защищает;
  **на внешний диск или в облако пока не скопирован** — это следующий шаг.
- **`backup/`** — снимки кода (и до `2026-10-16-101300-pre-originals` — ещё и `content/`) перед
  этапами работы. В 16 снимках с `2026-10-12-180954` по `2026-10-15-213848` есть копия `.env` — эти
  папки никуда не передавать. Последние снимки: `…-154854-pre-vimeo`, `…-161335-pre-srcset-original`,
  `…-163040-pre-gitignore`, `…-163746-pre-isolation` (код, тесты и весь `content/` перед изоляцией
  тестов). Не удалять.

## 5. Тесты

- **Тестовые данные:** `tests/fixtures/content/` (22 демо-проекта, `test-arara` — черновик, тексты сайта).
  `tests/conftest.py`: `make_content` копирует их во временную папку; фото демо-проектов генерируются
  синтетически (Pillow) один раз за прогон. Настоящие фото в тестах не используются.

## 7. Безопасность и ограничения

- `.env` — не в Git, не в публичные бэкапы и архивы, не открывать и не печатать; на сервере — свой
  `SECRET_KEY` и хеш пароля, созданные там.
- `content/originals/` — потенциально чувствительные метаданные (EXIF, GPS): не открывать наружу
  (nginx — только `content/media/`), не класть в Git.
- Не восстанавливать архив поверх рабочего `content/` без отдельного плана; проверка — во временной папке.
- `backup/` на том же диске — не полноценная резервная копия.
- Production-развёртывание и внешнее автоматическое резервное копирование **не выполнены**. Конфигурации
  nginx/gunicorn в репозитории нет; рекомендации — `content/README.md`, раздел «На боевом сервере»
  (`client_max_body_size 210m`, `proxy_read_timeout 120s`, gunicorn `--timeout 120`, ≥1 ГБ RAM на воркер,
  место под временные файлы загрузки и оригиналы).
- Без согласования: не менять дизайн, тексты сайта, CSS, анимацию, лимиты, обработку изображений, JSON
  контента; не ставить зависимости; не трогать файлы вне `CRVU` (кроме временной папки и памяти Claude)
  и конфигурацию OmniRoute; никаких разрушительных команд; не делать git commit/push и публикацию.
- Не запускать временные серверы на рабочих данных для проверок — использовать копию контента; не
  оставлять фоновых процессов.

## 8. Решения и почему

- Оригиналы — вне `media/`: `/media` отдаёт любые картинки этой папки, а в оригинале EXIF и геометка.
- Неудача обработки не теряет оригинал и не оставляет его в рабочей папке (→ история): так
  `portfolio.json`, `media/` и `originals/` согласованы.
- 200 МБ на запрос оставлено; при необходимости 5 × 40 МБ хватит 205 МБ.
- Обычные снимки декодируются по-прежнему ради качества (38 Мп 3:2 → ≈0,7 ГБ пика на загрузку);
  уменьшение с запасом 1,0 отвергнуто (потеря резкости). Панорамы — до ≈0,4 ГБ.
- В `srcset` основной файл добавлен ради чёткости на плотных экранах: на десктопе DPR 2 галерея может
  взять 2560 px (≈240 КБ вместо ≈165 КБ). Цена — ≈+40 мс сборки страницы на 1000 фото, ≈+11 % HTML.
- Тесты переведены на собственные данные, потому что рабочее портфолио меняется в админке.

## 9. Открытые вопросы

1. **Боевой сервер** не настроен и не проверен (раздел 7).
2. **Внешние резервные копии** не настроены; первый архив пока только на этом компьютере (раздел 4).
3. **Фото закрытой шторки портфолио грузятся с главной** (проверено: 3 из 5 карточек первого года,
   версии 640). Предложение без смены дизайна — `data-src`/`data-srcset` и подстановка в `main.js` при
   открытии шторки. Не делалось.
4. **Аудит сайта P0–P3** (плагины `frontend-design-audit:evaluate`, Playwright MCP,
   openai-security-best-practices) не проведён.
5. **Vimeo:** воспроизведение в автоматическом браузере не подтверждено (плеер загружается, Play
   нажимается, кадры не пошли — так же и вне сайта); проверить вручную в обычном браузере. Escape при
   фокусе внутри плеера не закрывает окно (ограничение iframe; «Закрыть» работает).
6. Мелочи: `/favicon.ico` → 404; кэш `/media` и `/static` — `no-cache`; HEIC не поддерживается;
   оригиналы и `.history/media` растут без автоочистки; при `SIGKILL` (OOM) часть пачки может остаться
   вне `portfolio.json` (оригиналы не теряются).

## 10. План работы

Лимиты: **файл — 40 МБ, запрос — 200 МБ, до 20 файлов, 100 Мп (PNG/WebP — 50 Мп)**; конфигурация
боевого сервера ещё требует проверки.

**А. Подготовка и загрузка фотографий.**
1. Скопировать первый архив (раздел 4) на внешний диск или в облако; следующие архивы создавать с
   `CRVU_BACKUP_DIR`, указывающим туда.
2. Подготовить фото (JPEG/PNG/WebP; HEIC → JPEG). Создать проекты в `/admin`, загрузить пачками
   (до 4 по 40 МБ), выбрать обложки, опубликовать.
3. После каждой сессии: `check-content`; число `NN.webp` в `content/media/portfolio/` совпадает с
   числом файлов в `content/originals/portfolio/`; новый архив.
4. Выбрать проекты для главной в редакторе и опубликовать.

**Б. Качество, размеры, форматы, отображение.** Выборочно сравнить оригинал и `NN.webp`/`-1920.webp`
(цвет, резкость, ориентация); в браузере (телефон и десктоп) — карточки `-640`, галерея по `srcset`;
решить по пункту 9.3; проверить Vimeo вручную (9.5).

**В. Анимация сборки стенда.** Сначала сформулировать задачу; учитывать вес кадров и мобильные;
`prefers-reduced-motion` уже обрабатывается. Бэкап перед правками; CSS/JS анимации — только по согласию.

**Г. Адаптивность и скорость.** Playwright MCP (390/768/1440): раскладка, шторки, галерея; сеть,
кэш-заголовки, favicon. Предложения — списком, без правок до согласования.

**Д. Финальное тестирование и запуск.** Полный `pytest`, `check-content`, проверка админки; аудит
P0–P3; настройка и проверка сервера; внешнее автоматическое резервное копирование и пробное
восстановление во временную папку.
